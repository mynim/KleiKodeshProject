# איך עובדים כאן — זרימת העבודה

מסמך זה מתאר **את הדרך שכל שינוי עובר**, מהרגע שמחליטים עליו ועד שהוא נכנס לפרויקט.
הוא כתוב בשפה פשוטה. לא נדרש ידע בתכנות כדי לעקוב אחריו.

- **מה נבנה ובאיזה סדר:** [docs/roadmap.md](roadmap.md)
- **סביבת הפיתוח והחסמים הטכניים:** [docs/fork-workflow.md](fork-workflow.md)

---

## המונחים, בשלוש שורות

| מונח | מה זה, בפשטות |
|---|---|
| **ענף** (branch) | מסלול עבודה נפרד. אפשר לשנות בו הכל בלי לגעת בקו הראשי. אם יצא לא טוב — זורקים את הענף וכלום לא נפגע |
| **קומיט** (commit) | "נקודת שמירה" עם הסבר מה נעשה. אפשר לחזור אליה תמיד |
| **PR** (Pull Request) | בקשה להכניס ענף אל הקו הראשי. זה המקום שבו **רואים את כל השינויים בצורה מסודרת** ומחליטים אם לאשר |
| **origin** | הפורק שלך — `github.com/mynim/KleiKodeshProject` |
| **upstream** | הפרויקט המקורי — `github.com/KleiKodesh/KleiKodeshProject` |

---

## הכלל המרכזי

> **שום דבר לא נכנס לפרויקט המקורי לפני שהוא נבנה והותקן ועבד כאן, במחשב הזה.**

הסדר הוא תמיד אותו סדר, ואי אפשר לדלג על שלב:

```
 ענף מקומי  →  בנייה  →  חבילת התקנה  →  בדיקה בוורד  →  PR בפורק שלך  →  PR בפרויקט המקורי
```

שתי נקודות העצירה החשובות:

- **אחרי שלב 4 (בדיקה בוורד)** — אם זה לא עבד, חוזרים אחורה. לא פותחים PR על משהו שלא נבדק.
- **אחרי שלב 5 (PR בפורק)** — זה הארגז החולי שלך. שם אתה רואה את כל השינוי בשלמותו לפני שהוא הופך לציבורי מול המפתח המקורי.

## שבעת השלבים

### שלב 1 — ענף חדש

כל שיפור מקבל ענף משלו, בשם שנקבע מראש ברשימת השיפורים.

```bash
git checkout master
git pull origin master
git checkout -b feat/word-ribbon
```

**למה ענף נפרד לכל שיפור:** כדי שאפשר יהיה לבדוק אחד בנפרד, להכניס אחד בלי השני, ולזרוק אחד שלא הצליח בלי לגעת בשאר.

**שמות הענפים:**

| תחילית | למה היא | דוגמה |
|---|---|---|
| `feat/` | תכונה חדשה | `feat/named-collections` |
| `fix/` | תיקון תקלה | `fix/search-filter-reset` |
| `docs/` | תיעוד בלבד, בלי קוד | `docs/fix-stale-plans` |
| `perf/` | שיפור מהירות | `perf/ftslib-numtypes-simd` |

---

### שלב 2 — בנייה

**לפני כל בנייה, בלי יוצא מן הכלל:**

```bash
git -C ChromeTabs pull --ff-only
```

רכיב הלשוניות יושב במחסן גיטהאב **אחר** ומתיישן בשקט. כשהוא לא מעודכן, הבנייה נכשלת בשגיאות שנראות כמו באג בקוד — ומבזבזות שעה על חיפוש במקום הלא נכון.

**פעם אחת בלבד, בהתקנה ראשונה במחשב** — תעודת החתימה:

```powershell
powershell -ExecutionPolicy Bypass -File Build\scripts\make-dev-cert.ps1
```

**ואז הבנייה עצמה:**

```powershell
msbuild KleiKodeshProject.slnx /p:Configuration=Debug /p:Platform=x64
```

**מה מחפשים בסוף:** `0 Error(s)`. כלום אחר לא נחשב הצלחה.

> ⚠️ **אזהרה מניסיון:** אם מריצים את הבנייה עם `| tail` או כל צינור אחר, קוד היציאה שמתקבל הוא של הפקודה האחרונה בצינור — **לא של הבנייה**. זו טעות שכבר הטעתה אותי כאן פעם אחת. עדיף להפנות לקובץ יומן ולבדוק אותו.

### שלב 3 — חבילת התקנה

בנייה מוצלחת היא לא התקנה מוצלחת. צריך לייצר את החבילה בפועל:

```
Build\build-menu.bat
```

התפריט מציע כמה אפשרויות. לבדיקה מהירה אפשר `Quick build` (התוסף בלבד); לבדיקה אמיתית צריך את הבנייה המלאה, שמייצרת גם קובץ התקנה.

**מה אמור להיווצר:**

| הקובץ | מה זה |
|---|---|
| `KleiKodeshVsto\bin\...\KleiKodesh.dll` | התוסף עצמו |
| `KleiKodesh.vsto` + `KleiKodesh.dll.manifest` | קובצי החתימה שוורד דורש כדי להסכים להתקין |
| `Build\Installer\KleiKodesh.pkg` | החבילה — כ‑46 מגה, 606 קבצים |
| `KleiKodeshSetup-vX.Y.Z.exe` | קובץ ההתקנה הסופי (בבנייה מלאה) |

### שלב 4 — בדיקה בוורד 🔴

**זהו השלב הקריטי, והוא זה שעוד לא נעשה כאן אף פעם.**

1. לסגור את וורד לגמרי.
2. להתקין את החבילה משלב 3.
3. לפתוח את וורד ולוודא שהלשונית של כלי קודש מופיעה.
4. לבדוק את השינוי עצמו — מה שכתוב "מה תראה" ברשימת השיפורים.
5. לבדוק שגם מה שעבד קודם ממשיך לעבוד.

**אם משהו כאן נכשל — עוצרים וחוזרים לשלב 1.** לא פותחים PR.

---

### שלב 5 — PR בפורק שלך

עכשיו, ורק עכשיו, השינוי עולה לגיטהאב:

```bash
git push -u origin feat/word-ribbon
gh pr create --repo mynim/KleiKodeshProject --base master
```

**מה כותבים ב‑PR** (בעברית, שתוכל לקרוא):

- מה השינוי, במשפט.
- לאיזה סעיף ברשימת השיפורים הוא שייך (למשל "א5").
- **מה נבדק בפועל** — באיזו גרסת וורד, ומה ראיתי במו עיני.
- מה **לא** נבדק.

**למה PR בפורק שלך ולא ישר למקור:** כאן אתה רואה את כל השינוי בתצוגה מסודרת, צבעונית, שורה־שורה — בלי להתקין כלום ובלי לקרוא קוד. זו הבדיקה שלך, לא של אף אחד אחר. אם משהו לא נראה לך — אפשר לתקן, או לסגור את ה‑PR, וכלום לא יצא לציבור.

---

### שלב 6 — מיזוג לקו הראשי של הפורק

אחרי שאישרת, השינוי נכנס ל‑`master` של הפורק שלך. מכאן הוא חלק מהגרסה שלך.

**ואם מחליטים לעצור כאן — זה בסדר גמור.** הפורק הוא שלך, וכל השיפורים יכולים לחיות בו בלבד. שלב 7 הוא בחירה, לא חובה.

---

### שלב 7 — PR בפרויקט המקורי

רק אם רוצים שהשינוי ייכנס גם לכלי קודש הציבורית:

```bash
gh pr create --repo KleiKodesh/KleiKodeshProject --base master --head mynim:feat/word-ribbon
```

**לפני שעושים את זה, שלושה דברים:**

1. **לסנכרן מול המקור** — אם המפתח שינה בינתיים אותם קבצים, צריך ליישב את זה **כאן**, לא אצלו.
2. **לוודא שאין בשינוי שום דבר מקומי** — התעודה שיצרנו, קובץ ההגדרות המקומי, או כל נתיב מהמחשב הזה.
3. **לזכור שזו פעולה פומבית בשמך.** היא נראית לכולם, היא מצריכה את זמנו של המפתח, ואי אפשר למחוק אותה לגמרי. **לא אפתח PR בפרויקט המקורי בלי שתאמר לי במפורש.**

| הקובץ | למה |
|---|---|
| `hb-mirror.json` | הגרסה האמיתית מכילה **מפתחות גישה לשרת אחסון**. מי שישיג אותם מקבל גישה. בפרויקט יושב ממלא מקום, וההגדרה מסתירה את האמיתי — אבל כדאי לדעת |

## סנכרון מול הפרויקט המקורי

הפורק **לא מתעדכן לבד**. כשיוצא עדכון אצל המפתח המקורי, צריך לבקש אותו:

```bash
git fetch upstream
git checkout master
git merge --ff-only upstream/master
git push origin master
```

**מתי לעשות את זה:** לפני פתיחת ענף חדש, ולפני PR לפרויקט המקורי.

**למה לא לכתוב ישירות על `master`:** כדי שהפקודה למעלה תמיד תעבוד בלי התנגשויות. `master` של הפורק הוא עותק נקי של המקור; כל מה שלנו יושב בענפים.

הפירוט המלא על סנכרון נמצא ב‑[docs/fork-workflow.md](fork-workflow.md).
